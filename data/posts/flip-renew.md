# AI와 함께 1년 전 프로젝트 되살리기 (1)

> [~~RENEW FLIP~~](http://3.27.214.203:3000)

발표가 끝나자 서버를 내렸다. SSAFY 마지막 팀 프로젝트로 만든 스마트 팩토리 물류 통합 관제 시스템 **FLIP**. 실제 AMR은 못 써서 로봇 20대를 시뮬레이터로 돌리고, 그 상태를 웹에서 실시간으로 봤다.

프론트 리드로 3D 관제와 실시간 데이터에 붙었다. 6주 만에 기업 연계 11개 팀 중 우수상을 받았는데, 백엔드와 인프라는 잘 모른 채 코드만 저장소에 남았다. 짧은 시연에서는 안 보이던 버그도 있었다.

1년 뒤에 저장소를 다시 열었다. 전체를 내 말로 설명할 수 있을 만큼 읽고, 지금 기준으로 고치고, 배포까지 가는 게 목표였다.

## 코드를 고치기 전에 문서부터

팀 프로젝트 때는 맡은 곳만 보다 보니, 1년 뒤에는 흐름이 한 번에 안 그려졌다. AI에게 수정을 맡기기 전에 코드를 읽고 적었다. 서비스 역할, 통신, 데이터가 도는 순서, 로컬에서 켜는 방법.

시뮬레이터가 로봇 20대의 위치, 배터리, 작업 상태를 만든다. 경로 계산 서버가 이동을 정하고, 관제 서버가 그걸 로봇에 넘긴다. 최신 상태는 저장소에 쌓이고, 프론트엔드는 대시보드와 3D 화면에 그린다.

실시간 위치와, 나중에 다시 볼 작업 기록을 왜 저장 방식을 나눴는지도 설명이 됐다. 로컬에서 다시 켜려면 데이터 저장이랑 메시지 전달 도구 버전이 맞아야 했다. 하나씩 깔다 깨져서 Docker Compose로 묶었다.

## 움직이는 것과, 제대로 도는 것은 달랐다

로컬에서 AMR이 움직이기 시작하자 문제가 보였다. 잠깐이면 그럴듯한데, 오래 보면 일부는 멈추고 서로 겹쳤다. 피하다가 생산 설비를 뚫고 지나가기도 했다.

### 첫 구간을 끝내고 그대로 서는 AMR

첫 이동은 끝나는데 다음 작업을 못 받고 섰다. 로그를 따라가니 작업을 부르는 이름이 서버와 데이터베이스에서 달랐다.

관제 서버는 이동이 끝나면 같은 이름 작업을 DB에서 찾아 기록한다. 이름이 다르니 처리를 멈추고, 다음 명령도 안 나갔다. 이름 규칙을 맞추고, 중간에 오류가 나도 다음 상태를 받게 정리 과정을 고쳤다.

### 같은 좌표에 겹치는 AMR

오래 돌리면 여러 대가 정확히 같은 위치에 겹쳤다. 길목을 쓰는 로봇이 있으면 나머지를 기다리게 되어 있었는데, 거의 동시에 진입을 요청하면 깨졌다.

비었는지 확인한 뒤에 사용 중이라고 표시했다. 그 틈에 두 대가 둘 다 “비어 있다”고 보고 같이 통과했다. 확인과 등록을 한 번에 묶었다. 먼저 온 한 대만 움직이고 나머지는 대기열에서 기다리게 했다.

### 피하다가 설비를 통과

처음엔 기본 경로가 잘못된 줄 알았다. 문제는 충돌을 피하려고 옆으로 비키는 동작이었다. 기본 경로에는 설비 위치가 들어가 있는데, 회피는 옆 로봇만 보고 방향을 잡아 설비 안으로 들어갔다.

설비 영역을 지도에 넣고, 비키는 경로 전체가 거기를 지나는지 보게 했다. 한쪽이 막히면 반대로, 양쪽이 막히면 억지로 안 움직이고 기다리게 했다.

## 화면을 관제실처럼

기존 화면은 파란 그라디언트와 그림자가 많아서 산만했다. v0에 기존 화면을 넣고 방향을 본 뒤 규칙을 다시 잡았다. 24시간 켜두는 관제실.

배경 효과를 줄이고 밝기로 중요도를 나눴다. 운행, 대기, 충전, 오류는 화면 어디서나 같은 색. 생산량이나 로봇 수처럼 자주 바뀌는 숫자는 비교하기 쉬운 글꼴로 바꿨고, 화면이 작아지면 중요한 것부터 보이게 배치했다.

## 대시보드도 3D처럼

3D 관제 화면은 이미 서버에서 위치와 작업을 실시간으로 받고 있었다. 대시보드 요약 카드와 생산량 차트만 5초마다 브라우저가 서버에 다시 물어봤다.

3D가 쓰던 실시간 연결을 대시보드에도 붙였다. 처음 들어올 때만 기존 방식으로 한 번 채우고, 이후엔 서버가 공장 상태와 생산량을 보내게 바꿨다. 공장 상태는 약 3초, 생산량은 약 5초 간격으로 들어오는지 직접 확인했다.

## 100ms마다 돌던 조회

AMR 실시간 상태를 보내려고, 저장된 데이터를 **100ms마다, 초당 10번** 통째로 읽고 있었다. 작은 단위로 나누게 바꿨고, 20만 개를 넣은 환경에서도 조회 중에 다른 요청을 받을 수 있는지 확인했다.

경로 저장도 비슷했다. 15개 구간을 저장하면서 필요한 정보를 15번 따로 조회하고 있었다. 한 번에 가져와 저장에서 다시 쓰니, DB 요청이 33번에서 19번으로 **42% 줄었다**.

## AWS에 올렸다

가상 서버 한 대에 올렸다. 내 컴퓨터에선 안 보이던 버전 차이와, 오래 돌리다 끊겼다 돌아온 AMR이 다시 작업을 못 받는 문제가 나왔다. 버전을 맞추고, 다시 붙은 AMR이 작업을 받게 고쳤다.

바로 코드를 고치지 않고 문서와 규칙, 작업 순서를 먼저 썼다. 구조를 적어 두고 Plan 모드에서 목표와 확인 기준을 정했다. 요구가 흐리면 AI가 추측하지 말고 먼저 물어보게 했다. 범위가 맞으면 구현 코드는 맡겼고, 프론트와 백엔드처럼 안 엮인 일은 병렬로 돌렸다.

맡긴 다음엔 실행하고 고치는 루프를 돌리고 테스트도 넣었다. 로봇 여러 대가 동시에 움직이는 시뮬레이터는 테스트를 만들어도 빈틈으로 버그가 나왔다. 한 번 고친 문제가 다시 나오는 것만은 막혔다.
