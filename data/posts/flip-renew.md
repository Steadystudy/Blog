# AI와 함께 1년 전 프로젝트 되살리기

> [현재 배포된 FLIP 바로가기](http://3.27.214.203:3000)

SSAFY 마지막 팀 프로젝트로 스마트 팩토리 물류 통합 관제 시스템 **FLIP**을 만들었다. 실제 AMR(자율주행 운반 로봇)을 사용할 수 없는 환경에서 로봇 20대가 공장 안을 이동하는 상황을 시뮬레이션하고, 그 상태를 웹에서 실시간으로 관제하는 프로젝트였다.

당시 프론트엔드 리드를 맡아 3D 관제 화면과 실시간 데이터 처리에 집중했다. 6주 동안 프로젝트를 완성해 기업 연계 11개 팀 중 우수상도 받았지만 아쉬움은 남았다. 발표가 끝난 뒤 서버는 내려갔고, 백엔드와 인프라는 충분히 이해하지 못한 채 코드만 저장소에 남아 있었다. 짧은 시연에서는 드러나지 않았던 버그도 있었다.

1년쯤 지난 뒤 저장소를 다시 열었다. 단순히 화면만 다시 띄우려는 것은 아니었다. 스마트 팩토리 3D 관제 시스템을 지금의 기준으로 다시 살펴보고, 실제 배포 환경까지 고려했을 때 개발자로서 더 손볼 부분이 없는지 확인하고 싶었다. 프로젝트 전체를 내 언어로 설명할 만큼 이해하고 개선하는 것, 그리고 그 과정을 포트폴리오로 남기는 것이 이번 작업의 목표였다.

## 첫 번째, 코드를 고치기 전에 문서부터 만들었다

저장소에는 사용자에게 화면을 보여주는 프론트엔드부터 로봇의 움직임을 계산하는 시뮬레이터, 데이터를 저장하고 전달하는 여러 서버까지 함께 들어 있었다. 팀 프로젝트 당시에는 각자 맡은 영역을 중심으로 개발했기 때문에, 시간이 지나자 전체 흐름을 한 번에 떠올리기 어려웠다.

그래서 AI에게 바로 코드 수정을 맡기지 않고 **코드를 읽고 문서화하는 일**부터 시작했다. 서비스별 역할과 통신 방식, 데이터가 이동하는 순서, 로컬 실행 방법을 하나씩 정리했다.

구조를 단순화하면 이렇다. 시뮬레이터가 실제 로봇 20대를 대신해 위치와 배터리, 작업 상태를 만든다. 경로 계산 서버는 각 로봇이 어디로 이동할지 정하고, 관제 서버는 그 결과를 받아 로봇에 전달한다. 로봇이 움직이면서 보낸 최신 상태는 저장소에 기록되고, 프론트엔드는 이 데이터를 받아 대시보드와 3D 관제 화면에 보여준다.

문서화하면서 이전에는 기능 이름으로만 알던 요소들이 연결되기 시작했다. 실시간으로 계속 바뀌는 로봇의 위치와 나중에 다시 확인할 작업 기록을 서로 다른 방식으로 저장하는 이유도 비로소 설명할 수 있게 됐다.

## 두 번째, Docker로 로컬 환경을 되살렸다

문서화를 마친 뒤에는 프로젝트를 내 컴퓨터에서 다시 실행했다. FLIP은 화면과 서버뿐 아니라 데이터를 저장하고 프로그램 사이에서 메시지를 전달하는 여러 도구가 함께 돌아가야 한다. 이를 하나씩 설치하면 버전과 설정이 달라져 같은 환경을 재현하기 어렵다.

그래서 Docker Compose로 각 프로그램의 실행 환경을 컨테이너에 고정하고, 전체 서비스를 같은 방식으로 실행할 수 있게 만들었다. 덕분에 기존 개발 환경을 비교적 빠르게 재현하고 이후 수정 사항도 동일한 조건에서 확인할 수 있었다.

## 세 번째, 움직이는 것과 정상 동작하는 것은 달랐다

로컬에서 AMR이 움직이기 시작한 뒤부터 진짜 트러블슈팅이 시작됐다. 잠깐 실행하면 그럴듯해 보였지만, 시간을 두고 지켜보면 일부 AMR이 멈추거나 서로 겹쳤다. 회피 동작 중 생산 설비를 뚫고 지나가는 일도 있었다.

### 첫 구간을 마친 AMR이 그대로 멈추던 문제

AMR은 첫 번째 이동까지는 정상적으로 마쳤지만, 다음 작업을 받지 못한 채 멈췄다. 화면 표시 문제인지, 경로 계산이 실패한 것인지부터 확인해야 했다. 로봇이 보낸 상태가 어느 단계까지 전달되는지 로그를 따라가 보니, 작업을 부르는 이름이 서버와 데이터베이스에서 서로 다르다는 사실을 찾았다.

관제 서버는 로봇이 이동을 마치면 같은 이름의 작업을 데이터베이스에서 찾아 기록한다. 하지만 양쪽의 이름이 달라 작업을 찾지 못했고, 그 순간 처리가 중단되면서 다음 이동 명령도 전달되지 않았다. 두 곳의 이름 규칙을 하나로 통일하고, 중간에 오류가 생겨도 다음 상태를 받을 수 있도록 정리 과정도 보완했다.

수정 후에는 첫 번째 이동이 끝난 뒤에도 기록이 정상적으로 저장됐고, AMR은 이어서 다음 작업을 수행했다. 화면에서는 단순히 로봇 한 대가 멈춘 것처럼 보였지만, 실제 원인은 서로 다른 프로그램 사이의 작은 약속이 맞지 않았기 때문이었다.

### 여러 AMR이 같은 위치에 겹치던 문제

시뮬레이션을 오래 실행하면 여러 AMR이 정확히 같은 위치에 겹치는 현상도 나타났다. 시스템은 원래 한 로봇이 길목을 사용하고 있으면 다른 로봇을 기다리게 만들었지만, 두 대가 거의 동시에 진입을 요청할 때 문제가 생겼다.

기존 방식은 먼저 길목이 비어 있는지 확인하고, 그다음 사용 중이라고 표시했다. 아주 짧은 순간에 두 로봇이 함께 확인하면 둘 다 “비어 있다”고 판단해 동시에 통행 허가를 받을 수 있었다. 그래서 빈자리 확인과 사용 등록을 한 번에 처리하도록 바꿨다. 먼저 도착한 한 대만 이동하고 나머지는 대기열에서 순서를 기다리게 하자, 여러 로봇이 같은 위치에 겹치던 현상이 사라졌다.

### 회피 중 생산 설비를 통과하던 문제

처음에는 기본 이동 경로가 잘못됐다고 생각했다. 하지만 확인해 보니 문제는 로봇끼리 충돌을 피하려고 잠깐 옆으로 비켜서는 동작에 있었다. 기본 경로에는 생산 설비의 위치가 반영되어 있었지만, 회피 동작은 주변 로봇만 보고 방향을 정해 설비 안쪽으로 들어갈 수 있었다.

생산 설비가 차지하는 영역을 지도에 표시하고, 로봇이 비켜서려는 경로 전체가 그 영역을 지나가는지 확인하도록 바꿨다. 한쪽이 막혀 있으면 반대쪽으로 피하고, 양쪽 모두 막혀 있으면 무리하게 움직이지 않고 기다리게 했다. 그 결과 AMR은 다른 로봇뿐 아니라 주변 설비까지 고려해 안전한 방향으로 움직였다.

## 네 번째, 오래된 화면을 관제 시스템답게 바꿨다

기능이 안정된 뒤에는 디자인을 손봤다. 기존 화면은 파란 그라디언트와 강한 그림자가 많아 각 요소가 서로 경쟁하고 있었다. v0에 기존 화면을 참고 이미지로 제공해 개선 방향을 탐색한 뒤, 프로젝트에 맞게 디자인 규칙을 다시 정리했다.

새로운 방향은 24시간 데이터를 지켜보는 관제실이었다. 화면 자체는 차분하게 두고, 실제로 변하는 수치와 로봇의 상태만 눈에 띄게 만들고자 했다.

배경의 강한 효과를 줄이고 밝기 차이로 정보의 중요도를 구분했다. 운행, 대기, 충전, 오류 상태에는 화면 어디서나 같은 색을 사용했다. 생산량이나 로봇 수처럼 자주 바뀌는 숫자는 한눈에 비교하기 쉬운 글꼴로 바꾸고, 화면 크기에 따라 중요한 정보부터 보이도록 배치도 조정했다.

AI로 만든 시안을 그대로 옮기지는 않았다. FLIP에는 이미 대시보드와 3D 관제 화면, AMR 목록, 상태 필터처럼 서로 연결된 기능이 있었다. 시안은 방향을 정하는 데 활용하고, 실제 화면은 기존 기능을 유지하면서 색상과 배치를 단계적으로 바꿨다.

## 다섯 번째, 대시보드의 정보를 더 자연스럽게 갱신했다

3D 관제 화면은 로봇의 위치와 작업 상태를 서버에서 실시간으로 받아오고 있었다. 반면 대시보드의 요약 카드와 생산량 차트는 브라우저가 5초마다 서버에 새로운 데이터가 있는지 다시 물어보는 방식이었다.

처음에는 새로운 기술을 추가해야 한다고 생각했다. 하지만 코드를 다시 살펴보니 3D 관제 화면에서 사용하던 실시간 연결을 대시보드에서도 활용할 수 있었다.

페이지에 처음 들어왔을 때는 기존 방식으로 데이터를 한 번 받아 화면을 바로 채웠다. 그다음부터는 서버가 새로운 공장 상태와 생산량을 보내주도록 바꿨다. 덕분에 브라우저가 계속 먼저 물어보지 않아도 대시보드의 정보가 자연스럽게 갱신됐다.

수정 후에는 공장 상태가 약 3초, 생산량이 약 5초 간격으로 들어오는지 직접 확인했다. 새 방식을 적용한 뒤에도 화면에 표시되는 데이터의 내용은 이전과 같게 유지했다.

## 여섯 번째, 보이지 않던 병목을 줄였다

화면과 기능이 정상적으로 보여도 내부 구현까지 효율적이라고 볼 수는 없었다. 실제 배포 환경에서 장시간 실행되는 상황을 가정하고, 자주 실행되는 코드와 반복되는 데이터베이스 요청을 살펴봤다.

### 한 번에 몰아서 찾던 데이터를 나누어 조회했다

AMR과 생산 라인의 상태를 찾을 때 저장된 데이터를 한 번에 모두 확인하고 있었다. 데이터가 적을 때는 문제가 없지만, 양이 많아지면 조회가 끝날 때까지 다른 요청이 기다려야 한다. 게다가 이 작업은 AMR의 실시간 상태를 보내기 위해 **100ms마다, 초당 10번** 반복되고 있었다.

그래서 데이터를 작은 단위로 나누어 찾도록 변경했다. 데이터 20만 개를 넣은 환경에서도 조회 중에 다른 요청을 함께 처리할 수 있는지 확인했다.

### 같은 데이터를 반복해서 찾는 횟수를 줄였다

AMR이 한 구간의 이동을 마치면 지나온 경로를 데이터베이스에 저장한다. 기존에는 경로 15개를 저장할 때 필요한 정보도 15번 따로 조회하고 있었다.

필요한 정보를 먼저 한 번에 가져온 뒤 저장 과정에서 다시 사용하도록 바꿨다. 같은 조건에서 데이터베이스에 요청하는 횟수는 33번에서 19번으로 줄어 **42% 감소**했다.

## 마지막, 로컬 성공을 실제 배포로 이어갔다

FLIP은 여러 프로그램이 함께 실행되어야 AMR 20대가 계속 움직인다. 실제 환경에서도 전체 시스템이 안정적으로 동작하는지 확인하기 위해 AWS의 가상 서버 한 대에 프로젝트를 배포했다.

배포 후에는 내 컴퓨터에서 보이지 않던 환경 차이와 장시간 실행 중의 연결 문제가 드러났다. 서버 환경과 맞지 않던 프로그램의 버전을 바꾸고, 연결이 끊겼다가 돌아온 AMR도 다시 작업을 받을 수 있도록 수정했다. 이 과정을 통해 배포는 단순히 결과물을 공개하는 일이 아니라, 로컬에서 놓친 문제를 확인하는 마지막 검증 단계라는 것을 배웠다.

## 프로젝트를 되살리며 배운 것

이번 작업에서 가장 크게 배운 것은 **AI를 효과적으로 활용하는 방법**이었다. AI에게 바로 코드 수정을 요청하기보다 먼저 문서와 규칙, 작업 순서를 준비하는 스캐폴딩이 중요했다. 프로젝트의 구조를 문서화하고 Plan 모드에서 목표와 확인 기준을 정하자, AI가 훨씬 안정적으로 의도한 방향을 따라왔다.

요구사항이 모호할 때는 AI가 임의로 판단하지 않고 먼저 나에게 질문하도록 했다. 인터뷰를 통해 내가 원하는 결과와 수정 범위를 맞춘 뒤에는 구현 단계의 코드를 100% 신뢰하고 맡겼다. 프론트엔드와 백엔드처럼 서로 독립적인 작업도 병렬로 진행하면서 속도를 높일 수 있었다.

코드를 신뢰한다는 것이 결과를 확인하지 않는다는 뜻은 아니었다. 구현이 끝난 뒤에는 실행과 수정을 반복하는 루프를 돌리고 테스트도 추가했다. 여러 로봇이 동시에 움직이는 시뮬레이터에서는 테스트를 만들어도 예상하지 못한 버그가 나타났지만, 적어도 한 번 해결한 문제가 되풀이되는 것은 막을 수 있었다.

결국 AI를 효과적으로 활용하려면 스캐폴딩과 인터뷰로 방향을 맞추고, 구현은 신뢰해 맡기되 결과는 반복 실행과 테스트로 확인해야 했다.
